## [0.9.0] — 2026-08-03

### Summary
Establishes a measured test-coverage and static-analysis baseline for the service. Coverage rises from 37% to 88.2% with the test count going from 42 to 175, and `mvn verify` now publishes coverage and code-quality metrics to SonarQube. **No application code was changed in this release** — every change is to the build configuration or to test sources. The new tests surfaced six defects in existing application code; these are recorded under Known Issues and are not fixed here.

---

### Added
- `jacoco-maven-plugin 0.8.15` in `pom.xml`, with three executions: `prepare-agent` at `initialize`, and `report` bound to **both** `test` and `verify`. The `test` binding means `mvn test` alone leaves a usable report at `target/site/jacoco/`; the `verify` binding guarantees the report exists before `sonar:sonar` reads it, independent of intra-phase plugin ordering.
- `sonar-maven-plugin 5.7.0.6970`, pinned. Invoking the goal unversioned resolves whatever is newest at run time — the version previously cached locally was `3.8.0.2131` (2021), too old for SonarQube 26.7.
- `sonar.projectKey`, `sonar.projectName`, `sonar.host.url` and `sonar.coverage.jacoco.xmlReportPaths` properties, so routine analysis needs only the token on the command line.
- `lombok.config` with `lombok.addLombokGeneratedAnnotation = true`. Lombok's `@Data`/`@Builder` generate well over a hundred methods per model class; this stamps them `@lombok.Generated`, which JaCoCo skips. Without it the `model`, `document` and `dto` packages are measured almost entirely on machine-written code. Compile-time only — no runtime effect and nothing added to the jar.
- 133 new tests in 13 new files:
  - `mapper` — 36 tests against the MapStruct-generated impls (`MasterEntityMapperImpl`, `EntityMapMapperImpl`, `CompetencyLevelMapperImpl`). Every service test mocks these mappers, so a wrong or missing `@Mapping` previously could not fail anything.
  - `reader` — 39 tests driving real CSV bytes through `MockMultipartFile` and real XLSX workbooks built in memory with POI, covering both readers and the reader factory.
  - `util` — 23 tests covering `EntityUtil`, `SheetUtil` and `RowProcessingResult`.
  - `controller` — 25 tests covering all 9 endpoints across both controllers plus all six `@ExceptionHandler` methods, via `MockMvcBuilders.standaloneSetup` with the real `ApplicationExceptionHandler`. No Spring context, so no database or OpenSearch is required.
- `EntityTypeExtension` — JUnit 5 `BeforeAllCallback` that loads `entity.entityTypeList` into `EntityType` for tests that do not boot Spring.
- `TestApplicationProperties` — binds the `entity-sheet.*` block from the deployed `application.properties` using Spring Boot's `Binder`, so reader and util tests exercise the shipped header lists and header→field mappings rather than a hand-maintained copy.

### Changed
- `.gitignore` — added `htmlReport/` (IntelliJ's coverage export; JaCoCo writes to `target/site/jacoco/`, already covered by `target/`) and `claude-kit/`.
- Three existing service test classes gained `@ExtendWith(EntityTypeExtension.class)`.
- `MasterEntityEsServiceImplTest` — the four `findEntitiesBySearchParameter` tests now capture the `NativeSearchQuery` handed to OpenSearch with an `ArgumentCaptor` and assert its clauses, replacing `verify(...).search(any(NativeSearchQuery.class), ...)`. The `any()` matcher discarded the one object those tests existed to verify, making all four satisfiable by any implementation. They are now mutually contradictory across branches: the fuzzy test requires `must().size() == 2`, the blank-language test requires `1`; the phrase test requires `MatchPhraseQueryBuilder`, the fuzzy test requires `MatchQueryBuilder`. `maxResults == 500` and the language lowercasing are also now asserted.
- `saveEntityDetailsInES` test — now asserts `createdBy` and `createdAt` on the captured documents. The `userId` parameter was added in v0.8.0 specifically so the impl could stamp these fields, but nothing verified it; both `setCreatedAt` and `setCreatedBy` could be deleted with the suite still green.

---

### Fixed
- **16 pre-existing test failures across all three service test classes.** `EntityType` holds its valid types in a static `Set` populated only by `EntityType.load()`, which runs from `EntityStartupApplicationRunner` at Spring startup. The Mockito-only service tests never boot a context, so the set stayed empty and every `EntityType.validate()` call at a service boundary threw `IllegalArgumentException: Invalid entityType: '…'. Allowed values: []` before the code under test was reached. Resolved in the test layer via `EntityTypeExtension`; no production code changed. `AastrikaEntityApplicationTests` was unaffected because it boots Spring.

### Known Issues

Defects in existing application code surfaced by the new tests. None are fixed in this release, none have TRIAGE IDs yet, and each is pinned by a test that documents current behaviour — those tests must be updated, not merely adjusted, when the underlying code is fixed.

| # | Area | Issue |
|---|---|---|
| 1 | `ApplicationExceptionHandler` | Every Spring MVC binding failure returns **HTTP 500 instead of 400**. The advice declares a catch-all `@ExceptionHandler(Exception.class)` and does not extend `ResponseEntityExceptionHandler`, so `ExceptionHandlerExceptionResolver` matches the catch-all before `DefaultHandlerExceptionResolver` runs. A missing `@RequestParam`, malformed JSON, wrong HTTP method or unsupported media type all report as server faults — misleading in monitoring, and 5xx-keyed retry logic will retry requests that can never succeed. |
| 2 | `SheetUtil` / `application.properties` | Two of the 26 configured CSV columns **cannot be parsed at all**. `created_date → createdDate` (`java.util.Date`) and `additional_properties → additionalProperties` (`Map`) receive the raw CSV String via `BeanWrapper`, which has no converter, throwing `TypeMismatchException`. That is not `IllegalArgumentException`, `IOException` or `UploadEntityException`, so it escapes all three catch blocks in `getCompiledEntitySheet` and surfaces as an unhandled 500. `EntityStartupApplicationRunner` does not catch this — it verifies only that the target field exists, not that a String can be converted into it. |
| 3 | `XlsxEntitySheetReader` | An **XLSX upload returns 200 and imports nothing**. `getCompiledEntitySheet` returns `Map.of()`, yet `supports()` accepts `.xlsx` and the factory advertises the reader at startup. `saveSheetDataIntoDB` then finds no entry for the global entity type, skips its body, leaves the upload tracker `null` and still returns `AppResponse.success`. The working `read()` method is not wired to the interface (its `@Override` is commented out) and maps neither `entity_type` nor `id`. |
| 4 | `MasterEntityServiceImpl:269` | `updateCompetencyLevel` calls `existingMasterEntity.getCompetencyLevels().stream()` with no null guard — an **NPE**, not a domain exception, whenever an update DTO carries `competencyLevels` with `entityType=COMPETENCY` but the loaded entity's collection is null. `toEntity(EntityCreateRequestDTO)` produces exactly that: `@Builder` discards the `= new ArrayList<>()` field initializer (the existing `MasterEntity.java:99` build warning). JaCoCo reports 0/4 branches on this method. |
| 5 | `MasterEntityMapper` | `toEntity(EntitySheetRow)` never sets `status` (the compiler's `Unmapped target property: "status"` warning), while `toDocument(EntitySheetRow)` hardcodes `status = "Active"` via `@Mapping(constant=…)`. One sheet upload therefore lands as **`Active` in OpenSearch and `null` in PostgreSQL**. |
| 6 | Dead code | `RowProcessingResult` (59 lines, referenced nowhere, near-duplicate of the in-use `BatchProcessingResult`); `EntityUtil.getMissingDataDetails` and `EntityUtil.buildMissedDataMap` (no callers, and both no-ops — the former assigns and discards its result, always returning an empty map); `EntityConflictException` (zero references); `MasterEntityMapper.toEntity(MasterEntityDocument)` (no callers, and throws `NumberFormatException` on the `code_language` id format this service actually writes). Deleting these removes roughly 30 lines from the coverage denominator with no loss of covered code. |

Open items already tracked in `docs/TRIAGE.md`, confirmed by execution data in this release:

- **T-009** — `EntitySheetProperties.Headers.getAllHeaders()` has no caller; JaCoCo confirms 0 of its 5 lines execute.
- **T-010** — `EntityMappingController` injects `EntityMappingServiceImpl` rather than the interface, so its test must mock the concrete class.
- **T-011** — `POST /v1/entity/upload` requires a `language` request param it never reads; omitting it fails the request (with a 500, per issue 1 above).
- **T-014 `[security]`** — `ApplicationExceptionHandler` returns the raw PostgreSQL root-cause message. ⚠ `EntityControllerTest.shouldMapDataIntegrityViolationToConflict` currently asserts that raw message, so it pins the behaviour T-014 says to sanitise. **Update that assertion when T-014 is fixed.**

### Migration Notes

No application behaviour changed. No database migration, no new environment variables, no configuration renames.

#### Build commands

```bash
# tests + local HTML coverage report; no server needed
./mvnw clean test

# tests + coverage + publish to SonarQube
./mvnw clean test sonar:sonar -Dsonar.token=<token>

# same, plus packaging
./mvnw clean verify sonar:sonar -Dsonar.token=<token>
```

`sonar.token` is deliberately absent from `pom.xml` per `SECURITY.md` §2.2 — pass it with `-Dsonar.token=…` or export `SONAR_TOKEN`. Omitting it fails with `HTTP 401 Unauthorized` during scanner bootstrap.

#### Reading the reports

`target/site/jacoco/index.html` leads with **instruction** coverage (93%); the **Lines** column holds line coverage (92.9%). SonarQube's headline `coverage` metric (88.2%) blends lines and conditions, which is why the three figures differ. Both tools identify the same uncovered code — 86 uncovered lines and 73 uncovered branches — and differ only in what they count as coverable (1,207 vs 998 lines).

#### Note for CI

If a surefire `<argLine>` is ever added to `pom.xml` it will **override** JaCoCo's agent argument and coverage will silently drop to 0%. Use `@{argLine}` to append rather than replace. This release does not set `argLine`.
